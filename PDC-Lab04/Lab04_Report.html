Task 1: Unsynchronized Counter (Shared-State Hazard)

Source Code (race.c)

#include <stdio.h> #include <pthread.h> #define NUM_THREADS 4 #define INCREMENTS_PER_THREAD 1000000 long counter = 0; void *worker(void *arg) { int i; for (i = 0; i < INCREMENTS_PER_THREAD; i++) counter++; return NULL; } int main() { pthread_t threads[NUM_THREADS]; int i; for (i = 0; i < NUM_THREADS; i++) pthread_create(&threads[i], NULL, worker, NULL); for (i = 0; i < NUM_THREADS; i++) pthread_join(threads[i], NULL); long expected = (long)NUM_THREADS * INCREMENTS_PER_THREAD; printf("Expected: %ld\n", expected); printf("Actual: %ld\n", counter); printf("Lost: %ld\n", expected - counter); return 0; }

Discussion Questions

1. Did the actual value ever equal the expected value? Were any two runs identical? Why is the result non-deterministic?

No the actual value never reached 4,000,000 in any of the 10 runs. And no two runs gave the same number either. This happens because the thread scheduler in the OS decides when to run each thread and that timing is different every time we run the program. Since counter++ is not an atomic operation, the threads keep overlapping and losing updates differently each time.

2. Using the load/add/store breakdown of counter++, explain how one increment can be lost.

So counter++ is actually 3 steps - first it loads the value from memory, then adds 1, then stores it back. If thread A loads counter and gets 5, but before it can store 6, thread B also loads counter and also gets 5. Then thread A stores 6, and thread B also stores 6. So we did 2 increments but counter only went from 5 to 6 instead of 5 to 7. One update got lost.

3. If INCREMENTS_PER_THREAD were reduced to 100, would the race disappear?

No the race condition is still there in the code. With only 100 increments the threads would finish so fast that they might not even overlap much, so the output could look correct. But thats just luck, the bug is still there. Just because the output looks right doesnt mean the program is safe from races.

Discussion Questions

1. Which line did TSan blame? Why are both accesses on the same line?

TSan pointed to line 12 which is where counter++ is. Both accesses show the same line because counter++ does a read and a write on the same variable, so when two threads run that same line at once their reads and writes conflict with each other on the same location.

2. How can TSan flag a race even when the final value looks correct?

TSan doesnt check if the output is right or wrong. It checks whether memory accesses are properly synchronized. So even if by luck the threads didnt interleave badly and the counter came out correct, TSan can still see that the accesses were not ordered by any lock or synchronization, and it reports the race anyway.

3. Task 1 showed the symptom; TSan shows the cause. Explain the difference.

In Task 1 we saw the symptom which was a wrong total. But sometimes the total might come out right by luck. TSan on the other hand finds the actual cause - it shows that threads are accessing the same memory without any synchronization. So we need tools like TSan because just testing the output is not enough to prove there are no races.

4. Why should the TSan build not be used for timing?

Because TSan adds a lot of overhead by instrumenting every memory access. It makes the program like 5-15x slower. So if we measured timing with TSan on, the numbers would be way off and not represent the actual performance of mutex vs atomic.

Task 3: Fixing the Race with a Mutex

Source Code (race_mutex.c)

#include <stdio.h> #include <pthread.h> #define NUM_THREADS 4 #define INCREMENTS_PER_THREAD 1000000 long counter = 0; pthread_mutex_t counter_lock = PTHREAD_MUTEX_INITIALIZER; void *worker(void *arg) { int i; for (i = 0; i < INCREMENTS_PER_THREAD; i++) { pthread_mutex_lock(&counter_lock); counter++; pthread_mutex_unlock(&counter_lock); } return NULL; } int main() { pthread_t threads[NUM_THREADS]; int i; for (i = 0; i < NUM_THREADS; i++) pthread_create(&threads[i], NULL, worker, NULL); for (i = 0; i < NUM_THREADS; i++) pthread_join(threads[i], NULL); long expected = (long)NUM_THREADS * INCREMENTS_PER_THREAD; printf("Expected: %ld\n", expected); printf("Actual: %ld\n", counter); printf("Correct: %s\n", (expected == counter) ? "YES" : "NO"); return 0; }

Discussion Questions

1. Was the actual value correct in all 10 runs? Why is this alone not conclusive?

Yes all 10 runs gave the correct answer 4,000,000. But just getting correct output isnt enough proof because we saw in Task 1 that a race can sometimes give a right-looking answer by coincidence. The real proof came from the TSan run which showed 0 warnings, confirming the synchronization is actually working properly.

2. main() reads counter after the joins without taking the lock. Why is that safe?

Because pthread_join() guarantees that once it returns, all the writes that thread made are visible to us. After joining all 4 threads, no other thread is running anymore so theres no one to race with. So reading counter without the lock is fine at that point.

3. What if only 3 of 4 threads used the lock?

Then we would still have a race. The 4th thread doing bare counter++ could interleave with the other threads even while they hold the lock, because the lock doesnt stop threads that dont use it. Every thread has to use the same lock for it to work.

4. Lock around each increment vs. around the whole loop?

If we lock around each single increment, the threads can take turns between increments so there is some parallelism but the overhead of locking/unlocking 4 million times is high. If we lock around the whole loop, each thread runs all its increments alone with no parallelism at all, but theres only 4 lock/unlock calls. Both give correct results. We used per-increment locking here to show minimal critical sections.

Task 4: Atomic Increment vs. Critical Section

Source Code (counter_bench.c)

#include <stdio.h> #include <pthread.h> #include <time.h> #define NUM_THREADS 4 #define INCREMENTS_PER_THREAD 1000000 long counter = 0; pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; void *worker_mutex(void *arg) { int i; for (i = 0; i < INCREMENTS_PER_THREAD; i++) { pthread_mutex_lock(&lock); counter++; pthread_mutex_unlock(&lock); } return NULL; } void *worker_sync(void *arg) { int i; for (i = 0; i < INCREMENTS_PER_THREAD; i++) { __sync_fetch_and_add(&counter, 1); } return NULL; } double get_time_ms() { struct timespec ts; clock_gettime(CLOCK_MONOTONIC, &ts); return ts.tv_sec * 1000.0 + ts.tv_nsec / 1000000.0; } void run_test(const char *name, void *(*func)(void *)) { pthread_t threads[NUM_THREADS]; int i; counter = 0; double start = get_time_ms(); for (i = 0; i < NUM_THREADS; i++) pthread_create(&threads[i], NULL, func, NULL); for (i = 0; i < NUM_THREADS; i++) pthread_join(threads[i], NULL); double elapsed = get_time_ms() - start; long expected = (long)NUM_THREADS * INCREMENTS_PER_THREAD; printf("[%s] expected=%ld actual=%ld correct=%s time=%.2f ms\n", name, expected, counter, (expected == counter) ? "YES" : "NO", elapsed); } int main() { run_test("mutex", worker_mutex); run_test("__sync_fetch_and_add", worker_sync); return 0; }

Discussion Questions

1. Did the atomic version produce correct total in every run?

Yes it did. All 5 runs gave exactly 4,000,000. Compared to Task 1 where the unsynchronized version was losing more than half of the updates, the atomic version works perfectly because __sync_fetch_and_add does the whole read-modify-write as one step that cant be interrupted.

2. Which was faster, and by how much? Why?

The atomic version was around 3.24 times faster. I think this is because mutex needs to make system calls for lock and unlock every single time, and it puts threads to sleep when they cant get the lock which adds overhead. The atomic operation is just one hardware instruction so its much lighter. No sleeping or waking up threads needed.

3. Even the atomic version is far slower than a single thread. Why?

Because all 4 threads are writing to the exact same variable. Every time one core updates counter, the cache line gets invalidated on all the other cores and they have to re-fetch it. This cache bouncing back and forth is called contention and it really slows things down even though theres no lock involved.

4. Example where atomic cant work but mutex can?

Like if you need to transfer money between two bank accounts - you have to subtract from one and add to the other, and both need to happen together. An atomic can only protect one variable at a time so it cant do both updates as a single unit. But with a mutex you can lock, update both variables, then unlock - so no one sees the state in between where money left one account but didnt arrive in the other yet.

5. How would the ratio change with 1 thread or more threads than cores?

With just 1 thread there is no contention at all so both would be fast and the ratio would be close to 1, maybe slightly above because mutex still has the overhead of lock/unlock calls even when nobody is contending. With more threads than cores like 8 or 16, the mutex version would get even worse because threads would get preempted while holding the lock and everyone else waits. The atomic version also gets slower but not as badly, so the ratio would probably get bigger.
